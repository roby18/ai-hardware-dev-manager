# 经验与踩坑库（lessons.md）

> 从真实项目（ESP32-S3 EasyInput V2.0，M0–M17）沉淀的可复用规则。每条：现象 → 根因 → 规则 → 来源。
> 分类：A 硬件事实 / B 烧录机制 / C 编译环境 / D 外设驱动 / E 调试 / F 工程实践。
> 使用方式：开发中遇到问题先按分类检索；新增经验按同样格式回填，并同步 SKILL.md 全局纪律（若属红线级）。

---

## A. 硬件事实

### A1 原理图 OCR 推断会错——以官方引脚表为准
- **现象**：低分辨率原理图放大识别引脚连线，推断出 2 处错误（KEY_WAKE 推断 GPIO20 实为 21；KEY2/8 推断 36/35 实为 47/48）。
- **根因**：分辨率不足时连线识别不可靠。
- **规则**：引脚事实权威分级 = 板厂官方引脚表 > 原理图 > PCB 照片/丝印 > OCR 推断 > 芯片通用知识。推断结果标 `推断` 并列入待验证；官方表到手立即纠正。
- **来源**：M1。

### A2 通用芯片机制 ≠ 板级操作流程
- **现象**：按通用 ESP32 惯例教用户"按住 BOOT + 上电"进下载模式、假设有 RESET 键——均被板厂官方纠正（实际：开机状态短按松开一次 BOOT；无独立 RESET 键）。
- **根因**：芯片通用机制（GPIO0 strapping）只能推出原理，推不出板子具体操作；未把供应商官方信息当最高优先级；原理图已有电路证据（AO6800 耦合复位）却视而不见。
- **规则**：凡给硬件操作指令，先标注「实测 / 供应商确认 / 推断待验证」三选一；推断类先问用户有无官方说明，不得以推断冒充事实。
- **来源**：M5。

### A3 外设供电域/使能链是"日志看不到的层"
- **现象**：提示音组件初始化全部 OK、播放无报错，但听不到声音。
- **根因**：功放供电域（V_SPK）经负载开关由 GPIO8 PWR_EN 控制，固件从未拉高 → 外设无电。
- **规则**：写驱动前先读原理图确认每个外设的供电域、负载开关、使能引脚、共享电源域；"软件全 OK 却无输出"先查供电/使能/硬件连接。共享域关断纪律：所有消费者停止并恢复安全引脚状态后才能关断。
- **来源**：M11。

### A4 复用脚与 strapping 脚是硬护栏
- **现象**：GPIO47/48 复用 SPI flash 时钟脚（SPICLK_P/N）；GPIO0 是下载 strapping 脚；GPIO19/20 USB-Serial/JTAG 与 USB OTG 复用同一物理脚。
- **规则**：硬件档案必须列出：已占用/空闲 GPIO 统计、复用脚警告（固件不得初始化对应冲突功能）、strapping 脚（不可当普通 IO）。
- **来源**：M1、M7。

## B. 烧录机制

### B1 flash 退出 0 ≠ 新固件已运行
- **现象**：esptool "Hard resetting via RTS" 后板子没跑新固件；用户 OFF→ON 断电重开才看到心跳。
- **根因**：手动进过下载模式的板子，RTS 复位不可靠，仍停在 ROM/下载状态。
- **规则**：手动进过下载模式的板子，烧完必须真正断电再上电；验证以应用健康证据（日志/心跳/物理现象）为准，不以 flash 退出码为准。
- **来源**：M5。

### B2 烧录前重扫端口 + 验 MAC，烧后不再次扰动
- **现象**：烧录/复位会让 USB 重枚举，端口名跨步骤缓存不可靠；多设备易烧错。
- **规则**：每次烧录前重扫端口、读芯片型号 + MAC、与用户确认；重枚举后重新验 MAC 一致才续烧。恢复正常启动后再跑 esptool 会重新扰动启动状态——验证以应用证据为准。
- **来源**：M5、esp-idf-cy 规约。

### B3 对照产物先验"烧的对不对"
- **现象**：BLE 键盘对照实验多次显示"键盘不可用"，实为 Kconfig choice 配置未生效，反复烧录的仍是 media 版（bin 内设备名 "ESP BLE HID2"）——假阴性浪费多轮。
- **规则**：凡烧录官方/参考产物，先用产物特征（bin 内设备名字符串）确认版本再上板。
- **来源**：M10。

## C. 编译环境

### C1 系统 Python 升级破坏 IDF 虚拟环境绑定
- **现象**：`idf.py` 报找不到 python 环境。
- **根因**：虚拟环境目录名编码了绑定的 Python 版本（`idf5.5_py3.11_env`），系统 Python 升 3.14 后官方 export 去找不存在的 py3.14 环境。
- **规则**：`IDF_PYTHON_ENV_PATH` 强制指回实际虚拟环境；激活脚本固定该变量。
- **来源**：M3、M6。

### C2 ccache 与并行编译在内存紧张时崩溃
- **现象**：编译随机失败 `OS Error 1450`、`std::bad_alloc`、CreateProcess 页面文件过小、系统卡死。
- **根因**：Rust 版 ccache 内存紧张崩溃；组件多时并行编译（cc1 单进程 1.5~2GB）超内存。
- **规则**：激活脚本里 **export 之后二次强制** `IDF_CCACHE_ENABLE=0` + `CMAKE_BUILD_PARALLEL_LEVEL=1~2`（官方 export 会覆盖前置设置，CMakeCache 会固化旧值）。
- **来源**：M3、M5、M7。

### C3 子项目编译需完整工具链 PATH
- **现象**：bootloader 子项目报 ASM 编译器 / CMAKE_MAKE_PROGRAM 错误。
- **根因**：直接调 ninja 时 PATH 缺工具链。
- **规则**：一切编译在激活脚本的完整环境下进行；不要裸跑 idf.py/ninja。
- **来源**：M4。

### C4 工具链 bin 缺失无前缀可执行文件
- **现象**：汇编失败，找不到 `as.exe`（实际只有 `xtensa-esp32s3-elf-as.exe`）。
- **规则**：缺前缀副本会导致 gcc 内部写死的调用失败，复制一份即可；此类环境修复记录进踩坑表。
- **来源**：M13。

## D. 外设驱动（I2S / USB / 按键）

### D1 I2S AUTO 分配会把 TX/RX 挤进同一控制器
- **现象**：麦克风 RX 与扬声器 TX 日志 `i2s controller 0 occupied`，RMS 异常。
- **根因**：AUTO 从 controller 0 起找空闲通道，TX/RX 挤进同一控制器组成 full-duplex 共享 BCLK/WS，时钟被低采样率一方覆盖。
- **规则**：多外设音频必须显式指定不同 I2S controller（`I2S_NUM_1` 隔离），不依赖 AUTO。
- **来源**：M15。

### D2 I2S 位宽/槽位不匹配会拆错样本
- **现象**：数据呈 `[0]=0x0000 [1]=0x00D4` 交替（一半为 0），RMS 被稀释约 √2。
- **根因**：slot 32bit + data 16bit 时，16bit 数据在 32bit 槽中被拆成 2 个 int16；PHILIPS 宏默认收 LEFT 但数据在右槽。
- **规则**：slot 位宽与读取方式一致（32bit 读 int32 取高 16 位）；采样率满足器件规格（如麦克风 WS 帧内需 64 SCK）；录音前用 debug 快照确认槽位（LEFT/RIGHT）与位宽。
- **来源**：M15、M16。

### D3 I2S DMA 环形缓冲会自动重播
- **现象**：提示音"响个不停"。
- **根因**：DMA 是环形缓冲，写满后通道保持 enable，循环重播旧样本。
- **规则**：播放结束必须 `i2s_channel_disable`（下次播放前再 enable），或写静音填满缓冲。
- **来源**：M11。

### D4 `i2s_channel_write` 超时参数是毫秒不是 tick
- **现象**：`playback write failed: ESP_ERR_TIMEOUT` 无声音。
- **根因**：误传 `pdMS_TO_TICKS(200)`=20ms，远小于 DMA 缓冲回填周期（~15ms/块），首个分块就超时。
- **规则**：I2S 阻塞写超时一律直传毫秒值；读源码确认参数单位（内部才转 ticks）。
- **来源**：M17.1。

### D5 阻塞写停止时延 = 块时长
- **现象**：循环回放中想停止，必须等整段播完。
- **根因**：`i2s_channel_write` 阻塞，整段写入后停止指令无法插入。
- **规则**：循环输出按 ~50ms 分块写，块间查状态机 → 停止时延 ≤ 块时长；回放 begin 在按键回调里同步完成，避免快速连按产生双任务竞态。
- **来源**：M17。

### D6 大缓冲不进任务栈
- **现象**：烧录后 boot 复位循环（用户以为板子烧坏）。
- **根因**：任务栈 4096 + 栈上缓冲 + ESP_LOGI 自身 ~1.5KB → 栈溢出，表现为复位循环而非报错。
- **规则**：大缓冲一律静态全局（任务只传指针）；任务栈按 ESP_LOGI 用量余量给（4096→8192）；排查先从栈算起。
- **来源**：M15、M16。

### D7 按键事件订阅按 GPIO 定位，不按名称字符串
- **现象**：KEY9 事件未触发，回退到普通键分支。
- **根因**：按名字 `"KEY9"` 匹配失败（表内实际名称 `"KEY9(PUSH)"`）→ 静默失败。
- **规则**：事件回调注册基于 GPIO 或稳定 id，名称只作展示。
- **来源**：M16。

### D8 TinyUSB 组件级坑（esp_tinyusb）
- **现象链**：① HID 接口没进描述符（电脑只认串口不认键盘）；② 链接报 undefined reference `tud_hid_get_report_cb`/`set_report_cb`；③ 按键长按重复输出；④ CDC COM 枚举正常但读不到日志。
- **根因**：① esp_tinyusb 1.7.x 自动配置描述符只含 CDC（无 CFG_TUD_HID 分支），需自定义复合描述符；② TinyUSB 0.21 这两个回调是强引用，应用必须实现（get 返回 0=STALL，set 空实现）；③ press/release 报告间隔 < 主机轮询周期，release 被覆盖 → press 后 `vTaskDelay(30ms)` 再 release；④ `tinyusb_cdcacm_write_queue` 依赖 CDC-ACM 接口实例，必须显式 `tusb_cdc_acm_init`。
- **规则**：用官方组件先读本机 IDF examples（`examples/peripherals/usb/device/tusb_hid`）；自定义描述符经 `tinyusb_config_t.configuration_descriptor` 传入；强引用回调补齐 stub；主机轮询类输出加间隔；read 不到数据先查初始化完整性。
- **来源**：M7。

### D9 组件/文件命名先查命名空间冲突
- **现象**：组件初名 `audio`，include 解析错误。
- **根因**：与 TinyUSB class/audio 目录冲突。
- **规则**：新建组件/文件前查目标框架内是否已有同名符号或目录；冲突立即改名。
- **来源**：M7 提示音（SPK_I2S）。

## E. 调试

### E1 软件日志全 OK 时，问题在"日志看不到的层"
- **现象**：I2S init OK / play OK / write 无失败，但无声。
- **规则**：排查顺序 = 供电/使能 → 硬件连接（人眼确认原理图连线）→ 外设规格（时序/增益）→ 软件。日志只证明软件路径执行了。
- **来源**：M11。

### E2 栈溢出表现为复位循环而非报错
- **现象**：boot 复位循环。
- **规则**：先算任务栈：ESP_LOGI ~1.5KB、缓冲大小、局部变量；大缓冲移出栈。见 D6。
- **来源**：M15。

### E3 串口独占：同一时间仅一个进程可用
- **现象**：`PermissionError(13, '拒绝访问')`，误以为程序未释放串口。
- **根因**：串口助手仍开着同一端口；VS Code ESP-IDF 插件残留 idf_monitor 进程占用。
- **规则**：串口助手 / VS Code Monitor / 脚本读取三选一，用完即关；烧录前 `Stop-Process` 清理残留 monitor；每次读取 finally Close。
- **来源**：M6、M7。

### E4 日志通道要在第 0 层定死
- **现象**：M5 第 0 层 printf 走 UART0，USB-Serial/JTAG 读不到；M7 CDC COM 枚举正常但无数据。
- **规则**：console 通道（UART / USB_SERIAL_JTAG / USB_CDC）在第 0 层决策并实机验证；周期心跳日志是"通道活着"的可靠信号（boot 段日志在 USB 枚举前输出会丢，属正常）。
- **来源**：M5、M7。

## F. 工程实践

### F1 逻辑与驱动分离，单一来源
- **现象**：无板子也要测逻辑；纯驱动代码无法在 PC 上验证。
- **规则**：把去抖/编码器解码/键码映射/波形生成/录音状态机等抽成零框架依赖纯 C，固件组件与 host 测试（w64devkit + Unity）共用同一份源码，杜绝两份代码漂移。改逻辑先跑 host 再回归固件。
- **来源**：M12、M14–M17。

### F2 host 测试会先抓测试自己的 bug
- **现象**：首跑 27 用例 3 个 FAIL，核对后全是用例期望值写错（负方向步数、正负抵消、去抖确认轮次），被测逻辑正确。
- **规则**：单元测试失败先质疑用例期望值（对照规格/源码重算），再质疑被测代码；期望值查库源码枚举（如 HID 键码查 hid.h）不凭记忆。
- **来源**：M12。

### F3 每里程碑提交 + 版本号从早期开始
- **规则**：每层闭环后 git commit + push，回复告知提交内容；`project(firmware VERSION x.y.z)` 从第一层就写入（M17.1 才补，前期固件无版本标识难管理）；读取版本需 main 组件 `PRIV_REQUIRES esp_app_format`。
- **来源**：M6.5、M17.1。

### F4 GitHub 推送：git 不读 Windows 系统代理
- **现象**：本机直连 github.com 443 超时，浏览器正常（走系统代理）。
- **规则**：读取系统代理（ProxyServer=127.0.0.1:10808）配置到仓库 local http.proxy/https.proxy 后 push；或 TUN 模式。
- **来源**：M13。

### F5 环境坑固化脚本要"二次强制"
- **现象**：ccache 复发两次才彻底固化。
- **根因**：官方 export.ps1 默认启用 ccache，覆盖激活脚本前置禁用；CMakeCache 固化旧值。
- **规则**：export 之后再次强制设置；固化后以"能稳定重跑完整编译"验证，不以"这次过了"为准。
- **来源**：M3、M5。

### F6 事实冲突处理优先级链
- **规则**：板级事实冲突按以下顺序裁决，并记录被取代关系：① 硬件负责人确认的实测 / 可复现 HIL 证据 → ② 当前批次 ECAD/BOM/装配资料与板级专项测试 → ③ 随项目打包的原理图/PCB 快照 → ④ 硬件档案合同文件 → ⑤ 用户指定目标项目的声明（只能描述项目选择，不能覆盖物理连线）→ ⑥ 历史迁移文档与网络通用教程。低优先级材料只能提供线索，不能覆盖更高优先级事实；没有足够证据时保留 `UNKNOWN`，不做"最像常规做法"的猜测。
- **来源**：easyinput-board-cy 事实冲突处理；本项目 M1。

### F7 证据升级阶梯，不冒充结论
- **规则**：区分证据等级且逐级升级：资料已确认 → 静态声明未见冲突 → 构建通过 → 烧录通过 → 应用日志通过 → 用户观察到物理现象 → 可复现 HIL 测试。没有相应证据时不要升级结论（"编译过"≠"功能对"，"烧录退出 0"≠"固件已运行"，"无报错"≠"外设已供电"）。
- **来源**：easyinput-board-cy 完成标准；本项目 M5/M7/M10/M11。
