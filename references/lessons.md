# 经验与踩坑库（lessons.md）

> 从真实嵌入式项目复盘沉淀的可复用规则。每条：现象 → 根因 → 规则。
> 分类：A 硬件事实 / B 烧录机制 / C 编译环境 / D 外设驱动 / E 调试 / F 工程实践。
> 使用方式：开发中遇到问题先按分类检索；新增经验按同样格式回填，并同步 SKILL.md 全局纪律（若属红线级）。

---

## A. 硬件事实

### A1 原理图 OCR / 推断识别会错——以官方资料为准
- **现象**：低分辨率原理图放大识别引脚连线，推断出错误引脚。
- **根因**：分辨率不足时连线识别不可靠。
- **规则**：引脚事实权威分级 = 实测 > 板厂官方引脚表/原理图 > 官方文档 > 网络文章。推断结果标 `推断` 并列入待验证；官方资料到手立即纠正。

### A2 通用芯片机制 ≠ 板级操作流程
- **现象**：按通用芯片惯例（如"按住 BOOT + 上电"进下载模式）操作，被板厂官方资料纠正。
- **根因**：芯片通用机制只能推出原理，推不出板子具体操作；未把供应商官方信息当最高优先级。
- **规则**：凡给硬件操作指令，先标注「实测 / 供应商确认 / 推断待验证」三选一；推断类先问用户有无官方说明，不得以推断冒充事实。

### A3 外设供电域/使能链是"日志看不到的层"
- **现象**：外设驱动初始化全部 OK、操作无报错，但功能不生效（如无声）。
- **根因**：外设供电域经负载开关由使能脚控制，固件从未拉高 → 外设无电。
- **规则**：写驱动前先读原理图确认每个外设的供电域、负载开关、使能引脚、共享电源域；"软件全 OK 却无输出"先查供电/使能/硬件连接。共享域关断纪律：所有消费者停止并恢复安全引脚状态后才能关断。

### A4 复用脚与 strapping 脚是硬护栏
- **现象**：某 GPIO 同时被 Flash 时钟、下载 strapping 或调试接口占用，初始化冲突导致异常。
- **规则**：硬件档案必须列出：已占用/空闲 GPIO 统计、复用脚警告（固件不得初始化对应冲突功能）、strapping 脚（不可当普通 IO）。

## B. 烧录机制

### B1 flash 退出 0 ≠ 新固件已运行
- **现象**：下载工具提示硬复位后板子没跑新固件；断电重开才看到心跳。
- **根因**：手动进过下载模式的板子，自动复位不可靠，仍停在 ROM/下载状态。
- **规则**：手动进过下载模式的板子，烧完必须真正断电再上电；验证以应用健康证据（日志/心跳/物理现象）为准，不以 flash 退出码为准。

### B2 烧录前重扫端口 + 验身份，烧后不再次扰动
- **现象**：烧录/复位会让 USB 重枚举，端口名跨步骤缓存不可靠；多设备易烧错。
- **规则**：每次烧录前重扫端口、读芯片型号 + MAC、与用户确认；重枚举后重新验 MAC 一致才续烧。恢复正常启动后再跑下载工具会重新扰动启动状态——验证以应用证据为准。

### B3 对照产物先验"烧的对不对"
- **现象**：对照实验多次显示功能不可用，实为烧录的仍是旧版/错版产物（如 bin 内设备名字符串不符）——假阴性浪费多轮。
- **规则**：凡烧录官方/参考产物，先用产物特征（bin 内设备名字符串等）确认版本再上板。

## C. 编译环境

### C1 系统 Python 升级破坏框架虚拟环境绑定
- **现象**：构建命令报找不到 Python 环境。
- **根因**：虚拟环境目录名编码了绑定的 Python 版本，系统 Python 升级后官方激活脚本去找不存在的环境。
- **规则**：环境变量（如 `IDF_PYTHON_ENV_PATH`）强制指回实际虚拟环境；激活脚本固定该变量。

### C2 缓存与并行编译在内存紧张时崩溃
- **现象**：编译随机失败（内存错误、进程被杀、系统卡死）。
- **根因**：编译缓存（如 ccache）内存紧张崩溃；组件多时并行编译超内存。
- **规则**：激活脚本里 export 之后**二次强制**禁用缓存 + 限并行度（官方 export 会覆盖前置设置，构建缓存会固化旧值）。

### C3 子项目编译需完整工具链 PATH
- **现象**：bootloader 等子项目报缺少编译器 / 构建工具。
- **根因**：直接调构建器时 PATH 缺工具链。
- **规则**：一切编译在激活脚本的完整环境下进行；不要裸跑构建命令。

### C4 工具链缺无前缀可执行文件
- **现象**：汇编失败，找不到 `as.exe`（实际只有带前缀的 `xxx-elf-as.exe`）。
- **根因**：编译器内部写死调用无前缀名称。
- **规则**：缺前缀副本会导致内部调用失败，复制一份即可；此类环境修复记录进踩坑表。

## D. 外设驱动

### D1 同类外设自动分配可能挤进同一控制器
- **现象**：两个同类型外设（如音频 RX/TX）日志显示控制器被占用，数据异常。
- **根因**：自动分配从首个控制器起找空闲通道，可能组成共享时钟的全双工配置，时钟被低采样率一方覆盖。
- **规则**：多外设同类功能必须显式指定不同控制器/通道，不依赖自动分配。

### D2 位宽/槽位不匹配会拆错样本
- **现象**：数据呈规律性半零交替，有效值被稀释。
- **根因**：槽位位宽与数据位宽不一致时，数据在槽中被拆成多份；默认宏可能收错槽。
- **规则**：槽位位宽与读取方式一致；采样率满足器件规格；上线前用调试快照确认槽位与位宽。

### D3 DMA 环形缓冲会自动重播
- **现象**：一次性输出"持续不停"。
- **根因**：DMA 环形缓冲写满后通道保持使能，循环重播旧数据。
- **规则**：输出结束必须停用通道（下次输出前再使能），或写静音填满缓冲。

### D4 阻塞写超时参数注意单位
- **现象**：输出写入报超时、无效果。
- **根因**：误把毫秒当 tick（或相反）传参，远小于实际周期，首个分块就超时。
- **规则**：阻塞写超时一律按接口文档单位传值；读源码确认参数单位，不凭记忆。

### D5 阻塞写停止时延 = 块时长
- **现象**：循环输出中想停止，必须等整段播完。
- **根因**：阻塞写整段写入后停止指令无法插入。
- **规则**：循环输出按小块分块写，块间查状态机 → 停止时延 ≤ 块时长；在回调里同步启动输出时注意快速连续触发产生竞态。

### D6 大缓冲不进任务栈
- **现象**：烧录后启动复位循环（误以为硬件损坏）。
- **根因**：任务栈 + 栈上大缓冲 + 日志库自身占用 → 栈溢出，表现为复位循环而非报错。
- **规则**：大缓冲一律静态全局（任务只传指针）；任务栈按日志库用量给余量；排查先从栈算起。

### D7 事件订阅按稳定的硬件标识定位，不按名称字符串
- **现象**：某事件未触发，静默回退到默认分支。
- **根因**：按名称字符串匹配失败（实际名称带后缀等）→ 静默失败。
- **规则**：事件回调注册基于 GPIO 或稳定 id，名称只作展示。

### D8 用框架组件先读官方示例
- **现象链**：① 接口没出现在预期位置（如 HID 描述符缺）；② 链接报强引用回调未实现；③ 快速触发输出被覆盖；④ 枚举正常但收不到数据。
- **根因**：组件默认配置不含所需分支；框架强引用回调应用必须实现；输出间隔小于对端轮询周期被覆盖；数据接口依赖显式初始化。
- **规则**：用官方组件先读本机 SDK examples；需要时自定义配置描述符；强引用回调补齐 stub；对端轮询类输出加间隔；收不到数据先查初始化完整性。

### D9 组件/文件命名先查命名空间冲突
- **现象**：新组件 include 解析错误。
- **根因**：与框架内置同名符号或目录冲突。
- **规则**：新建组件/文件前查目标框架内是否已有同名符号或目录；冲突立即改名。

## E. 调试

### E1 软件日志全 OK 时，问题在"日志看不到的层"
- **现象**：初始化/操作均无报错，但功能不生效。
- **规则**：排查顺序 = 供电/使能 → 硬件连接（人眼确认原理图连线）→ 外设规格（时序/增益）→ 软件。日志只证明软件路径执行了。

### E2 栈溢出表现为复位循环而非报错
- **现象**：启动复位循环。
- **规则**：先算任务栈：日志库开销、缓冲大小、局部变量；大缓冲移出栈。见 D6。

### E3 串口独占：同一时间仅一个进程可用
- **现象**：访问串口报权限拒绝，误以为程序未释放。
- **根因**：串口助手仍开着同一端口；编辑器插件残留 monitor 进程占用。
- **规则**：串口助手 / 编辑器 Monitor / 脚本读取三选一，用完即关；烧录前清理残留 monitor；每次读取 finally 关闭。

### E4 日志通道要在第 0 层定死
- **现象**：启动日志走默认通道，目标调试接口收不到；枚举正常但无数据。
- **规则**：console 通道（UART / USB_SERIAL_JTAG / USB_CDC）在第 0 层决策并实机验证；周期心跳日志是"通道活着"的可靠信号（boot 段日志在枚举前输出会丢，属正常）。

## F. 工程实践

### F1 逻辑与驱动分离，单一来源
- **现象**：无板子也要测逻辑；纯驱动代码无法在 PC 上验证。
- **规则**：把去抖/解码/状态机/波形生成等抽成零框架依赖纯 C，固件组件与 host 测试共用同一份源码，杜绝两份代码漂移。改逻辑先跑 host 再回归固件。

### F2 host 测试会先抓测试自己的 bug
- **现象**：首跑多个用例 FAIL，核对后全是用例期望值写错，被测逻辑正确。
- **规则**：单元测试失败先质疑用例期望值（对照规格/源码重算），再质疑被测代码；期望值查库源码枚举，不凭记忆。

### F3 每里程碑提交 + 版本号从早期开始
- **规则**：每层闭环后 git commit + push，回复告知提交内容；版本号从第一层就写入（后期才补，前期固件无版本标识难管理）。

### F4 环境坑固化脚本要"二次强制"
- **现象**：同一环境坑反复复发。
- **根因**：官方激活脚本默认值覆盖前置设置；构建缓存固化旧值。
- **规则**：export 之后再次强制设置；固化后以"能稳定重跑完整构建"验证，不以"这次过了"为准。

### F5 事实冲突处理优先级链
- **规则**：板级事实冲突按以下顺序裁决，并记录被取代关系：① 硬件负责人确认的实测 / 可复现 HIL 证据 → ② 当前批次 ECAD/BOM/装配资料与板级专项测试 → ③ 随项目打包的原理图/PCB 快照 → ④ 硬件档案合同文件 → ⑤ 用户指定目标项目的声明（只能描述项目选择，不能覆盖物理连线）→ ⑥ 历史迁移文档与网络通用教程。低优先级材料只能提供线索，不能覆盖更高优先级事实；没有足够证据时保留 `UNKNOWN`，不做"最像常规做法"的猜测。

### F6 证据升级阶梯，不冒充结论
- **规则**：区分证据等级且逐级升级：资料已确认 → 静态声明未见冲突 → 构建通过 → 烧录通过 → 应用日志通过 → 用户观察到物理现象 → 可复现 HIL 测试。没有相应证据时不要升级结论（"编译过"≠"功能对"，"烧录退出 0"≠"固件已运行"，"无报错"≠"外设已供电"）。
