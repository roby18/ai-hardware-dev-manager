# 六阶段操作手册（phases.md）

> 本文件是 SKILL.md 的展开版：每个阶段的**目标、输入、动作序列、验收清单、常见坑与真实示例**。按当前所处阶段只读对应小节。
> 示例与坑来自真实嵌入式项目复盘，以通用形式呈现，不绑定特定板子或机器。

---

## P0 需求与决策基线

**目标**：把"想做的东西"变成可拍板的 MVP 范围与决策记录，避免开发中反复返工。

### 输入收集
- 用户一句话需求 + 目标用户/场景
- 硬件形态（板子型号、板上资源：按键/旋钮/LED/麦/喇叭/屏幕等）
- 交付目标（原型演示 / 教学视频 / 量产样机）

### 动作序列
0. **访谈节奏**：整个摸底期采用**分步访谈**——一次只推进一个阶段，每阶段只问 3–6 个问题，等用户回答后再进下一阶段，不一次性甩问卷；回答随手存进 `hardware/intake-notes.md`（防长对话丢失），后续所有产物以它为依据。用户答不上来 → 标 `[unknown]` 并附**获取动作**（查哪份文件 / 跑哪条命令 / 量哪里 / 问厂家什么），列入待办，不卡住、不猜。
1. 澄清"烧板子"等风险认知，建立安全基线（供电错误/短路/GPIO 直驱大负载才是物理烧毁主因；配错引脚多为启动失败/烧录失败/行为错乱）。
2. 建立协作基线：不猜不编、先征同意、证据分级、知识来源边界。
3. **阶段 0 · 项目意图与边界**：一句话目标 + 可观察成功标准（怎么算"成了"）+ 明确"不做什么"（非目标）+ 必须兼容的既有契约（上位机 App / 协议 / 外壳 / 已量产板）。
4. 写 `requirements.md`：MVP 功能 F1..Fn、P1/P2 扩展路线、验收标准。
5. 关键决策点**逐项结构化拍板**（一次问一组，问完落文档）：
   - 连接方式（USB / BLE / 双模谁优先）
   - 输出协议（HID / 自定义 / 串口）
   - 配置方式（编译期 / 运行时）
   - 每个输入件的功能（旋钮→音量？长按？）
   - 状态指示（哪颗灯、什么含义）
   - 开发框架（ESP-IDF / Arduino / 其他）——按项目约束选，不默认
6. 决策表落 `requirements.md`（决策点/结论/时间），后续变更走版本记录。

### 验收清单
- [ ] requirements.md 存在：MVP 范围、验收标准、决策表、扩展路线
- [ ] 每个决策点有结论且记录时间，无"待定"
- [ ] 用户确认过范围（口头上即可，关键项记录）

**常见坑**：决策含糊就开工 → 后续每层都返工。交互类决策（如录音交互）尤其要先拍板——这类设计改了两轮才定。

## P1 硬件摸底（引脚表冻结）

**目标**：在写任何 GPIO 代码前，把硬件事实钉死。**整个流程最重要的阶段——引脚表错了，后面全错。**

### 输入收集（按权威等级排优先级）
0. **实测结果**（万用表测通断、esptool 读 flash_id、上机扫描 I2C 地址）——最高权威，事实冲突时以实测为准
1. **板厂官方引脚映射表**（截图/文字）——官方权威
2. 原理图（逐页精读，放大核对芯片引脚区）
3. PCB 正/反面照片、丝印、购买链接
4. 器件 datasheet（外设规格，如麦克风 WS 帧周期、功放时序）
5. 网络文章/教程——只作线索，回到原理图或官方来源核对

### 动作序列（分步访谈，按序推进，每阶段 3–6 问，随问随存 `hardware/intake-notes.md`）
0. 启动前确认三件事：工程根目录绝对路径、芯片/SDK 家族（ESP-IDF / Arduino / STM32 等）、板子是否在手（决定哪些字段能实测、哪些先标 `[unknown]`）。
1. **阶段 1 · 芯片与模组身份**：确切型号与封装（如 ESP32-S3-WROOM-1 N16R8）、模组后缀编码（Flash/PSRAM 容量与类型）、SDK 版本、板子型号/购买链接/原理图 PDF（放入 `hardware/`）。
2. **阶段 2 · 下载、供电与调试链路**：USB 是芯片原生 USB（S3 为 GPIO19/20）还是 USB-UART 桥（CH340/CP2102，看 USB 口旁芯片丝印）；供电方式/工作电压/电流预算；调试方式；BOOT/RESET/自动下载电路。
3. **阶段 3 · 电源与危险区**：共用电源轨/负载开关/使能脚与上下电时序；上电默认电平会否导致外设误动作；逐一核对 strapping 脚。**"错了可能烧件/变砖"的内容进硬件档案「危险区」章节与红线清单。**
4. **阶段 4 · 逐外设引脚事实**：按外设逐个收集小表：信号名 → GPIO → 方向 → 上下拉 → 上电默认态 → 电压域 → 来源（原理图网络名/实测/厂家例程宏）。无原理图时明确告知：引脚事实只能来自厂家例程宏/丝印/万用表测通断，bring-up 时逐个验证。
5. **阶段 5 · 对外通信契约**：USB HID / BLE / 串口 / 网络协议先定义报文/能力/版本协商再写代码；设备名/VID/PID 有对端软件时一律冻结；分区表/NVS 布局标记"冻结，修改需评估变砖风险"。
6. **阶段 6 · 构建环境与工具链**：SDK 路径与多版本归属（以 build/CMakeCache.txt 为准）；OS 与内存、低并发构建设置（`IDF_PY_BUILD_JOBS=2` 等）；烧录串口与"烧录必须人工确认目标设备"。
7. **阶段 7 · 确认与缺口清单**：输出完整事实摘要（表格），`[unknown]` 汇总为"上板前必须补齐 / 可边做边补"两类；用户确认后才生成工程骨架；事实冲突（厂家资料 vs 实测）当面指出，以实测为准。
8. 建 `hardware-archive.md`（模板见 `assets/hardware-archive.template.md`），章节固定：
   - 板子标识（产品名/丝印/主控/Flash/晶振）
   - 板上资源清单（器件/数量/GPIO 关联）
   - **电源系统与供电/使能链**（负载开关、使能引脚、共享电源域——"软件全 OK 却无输出"的常见根因）
   - **完整 GPIO 映射表（每行带来源列）**
   - 引脚占用统计与注意事项（复用/占用/strapping 警告）
   - **BOOT/下载/复位机制（供应商官方确认）**
   - **危险区（烧件/变砖风险项 + 红线）**
   - 待实物验证项清单
9. **芯片约束逐引脚反查**：每个引脚写入引脚表前，用目标芯片约束参考反查一次（strapping pin、仅输入、电源域、被 Flash/PSRAM 占用）；ESP32-S3 快速反查见 `references/esp32-s3-constraints.md`，其他芯片现查官方 datasheet。
10. 每项事实标来源；低分辨率图 OCR 推断结果标 `推断` 并列入待验证——OCR 推断可能出错，官方资料到手必须纠正。
11. 输出"待实物验证项"（极性、方向、干扰、分压比等），在 P3/P4 尽早闭环；同时生成 `docs/hardware/bring-up-checklist.md`（模板见 `assets/bring-up-checklist.template.md`）。

### 验收清单（门禁：**引脚表 100% 冻结且来源可溯**）
- [ ] GPIO 映射表每行有来源列，无"我觉得/应该是"
- [ ] 供电/使能链（外设电源域、使能引脚）已从原理图确认
- [ ] BOOT/下载/复位机制有供应商官方确认或明确标注"待验证"
- [ ] 待实物验证项清单存在，每项有验证方法

**常见坑**：用芯片通用知识写板级引脚（GPIO0 当普通按键用）；忽略复用脚；不查供电使能链。

## P2 环境基线

**目标**：开发环境可用且可复现，环境坑固化进脚本，不再重复踩。

### 动作序列
1. **探测现有环境**（不假定"没装"）：IDF 版本、工具链、Python 虚拟环境、串口、网络。读 `build/project_description.json` 的 idf_path、`IDF_PATH`、EIM 登记、惯例路径。
2. 环境坑逐一解决并**固化进一键激活脚本**（`esp-idf-env.ps1` 范式）：
   - 固定 `IDF_PATH` / `IDF_TOOLS_PATH` / `IDF_PYTHON_ENV_PATH`
   - **export 之后二次强制**环境变量（官方 export 会覆盖前置设置——ccache 复发两次才彻底固化）
   - 禁 ccache（内存紧张时 Rust 版 ccache 崩溃）、限并行度（`CMAKE_BUILD_PARALLEL_LEVEL`）
3. 验证：`idf.py --version` 真实输出；用目标芯片构建最小示例。
4. 网络受限时的问题与解法（代理/镜像等）作为个人环境经验保存在项目文档，不回填本 Skill——保持通用性。

### 验收清单
- [ ] 一键激活脚本存在且幂等可重跑
- [ ] 一条命令完成环境装配 + 编译（同一条命令内 source + idf.py）
- [ ] 踩坑表记录：现象/根因/解法/固化位置

**常见坑**：系统 Python 升级破坏 IDF 虚拟环境绑定（目录名编码了 Python 版本）；ccache 与并行编译在内存紧张时崩溃；bootloader 子项目需完整工具链 PATH。

## P3 骨架与第 0 层

**目标**：最小固件上板可运行、日志通道定死，之后每层都有可靠观测手段。

### 动作序列
1. 标准工程结构（`idf.py create-project`）。
2. `pin_config.h`：全部引脚宏，**唯一来源 = hardware-archive.md**，加注释来源。
3. 第 0 层 = 启动日志 + 引脚表摘要打印 + 状态灯（心跳）。
4. **日志通道先行决策并实机验证**：
   - UART 排针是否焊接？USB-Serial/JTAG 与 USB OTG 是否复用同一物理脚？
   - console 三选一：UART / USB_SERIAL_JTAG / USB_CDC（TinyUSB），第 0 层定死
   - 示例：USB 为原生接口（调试与设备功能复用同一物理脚）时，console 可走 USB-Serial/JTAG 或用 USB CDC 转发日志；UART 排针未引出时 UART 不可用
5. 烧录：重扫端口 → 验 MAC → 用户确认 → flash → 断电重开 → 观察日志/心跳。
6. **定义第一个验证任务（任务书）**：以 bring-up 清单第一级为起点，任务书必须含：可观察的验收标准（看到哪行日志 / 灯以什么频率亮灭）、明确实现边界（只允许用 `pin_config.h` 中的宏）、烧录由用户人工执行、完成后回写 PROJECT_LOG.md。

### 验收清单（门禁）
- [ ] 编译通过（记录固件大小/分区余量）
- [ ] 实机烧录成功且**断电重开后**日志/心跳可观测
- [ ] 日志通道验证通过（能持续读到日志，不是只看 boot 段）
- [ ] BOOT/下载流程按板子真实机制执行（供应商确认优先）

**常见坑**：日志通道没提前定 → 读不到日志、CDC 无数据；boot 段日志在 USB 枚举前输出会丢（正常，用周期心跳验证）。

## P4 逐层功能（每层一个闭环）

**目标**：一次只加一个能力，每层独立可验证、可回退。分层粒度按依赖排：按键扫描 → HID → 编码器 → BLE → 音频 → LED → 录音…（示例顺序，按项目依赖调整）。

### 每层动作序列（闭环）
1. **方案先行**：先读官方示例/组件文档（本机 SDK examples 是最快参考），再动手。组件/文件命名先查命名空间冲突（如组件名与框架内置符号冲突 → 改名）。
2. **交互/范围先拍板**：新交互用结构化提问一次问清（如录音触发方式、回放控制）。
3. **逻辑抽纯 C + host 测试**：把无硬件依赖的逻辑（去抖状态机、编码器解码、键码映射、波形生成、录音状态机）抽成零框架依赖文件，固件组件与 host 测试**共用同一份源码**（单一来源，杜绝漂移）。
4. 编译（限并行度）→ 烧录 → 实机验证。
5. **实机验证前先验"烧的对不对"**：bin 内特征（设备名字符串）确认烧的是预期版本。
6. 每层通过后：git commit + push + PROJECT_LOG 更新（结论/排查路径/根因/沉淀）。

### 实机验证要点
- 分层闭环：编译过 ≠ 功能对，必须以真机行为为准（串口日志/物理现象/主机端行为）。
- 对照实验也要先验烧的版本（官方对照版可能实为另一配置，假阴性浪费多轮）。
- 串口验证注意独占（同一时间一个进程）。

### 验收清单（门禁）
- [ ] host 测试全绿（该层相关用例）
- [ ] 实机行为符合验收标准（有日志/现象证据）
- [ ] git 已提交并 push，提交内容告知用户
- [ ] PROJECT_LOG 已更新该层里程碑

## P5 验证与交付

### 动作序列
1. 全量 host 回归 + 固件回归编译。
2. 实机最终验收（用户实测确认）。
3. 版本号：`project(firmware VERSION x.y.z)` 写入 app 描述符，启动日志 + 构建日志双可见。
4. 文档：README（环境要点/烧录步骤/可调参数/FAQ）+ 使用说明书；关键机制配图（可视化）。
5. GitHub 同步（.gitignore 正确，无敏感文件入库）。

### 验收清单
- [ ] host 全绿 + 固件编译通过
- [ ] 实机验收记录（用户确认）
- [ ] 版本号可见、文档完整
- [ ] 仓库同步完成
